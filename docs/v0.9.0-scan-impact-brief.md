# greenbump v0.9.0 开发任务:确定性预览(--scan 影响面分析)

## 为什么做这个

竞品 Emend 的杀手级特性是 `emend scan`:**不调 LLM、零成本、静态分析**就能告诉用户"升级 zod 3→4 会影响你的 4 个文件、12 处代码"。这是它的获客入口——用户不用配 API key 就能看到价值。

greenbump 的 `--scan` 现在只列出过时依赖的名字和版本,太弱了。本任务把它升级为**影响面分析预览**,直接对标 Emend。

## 核心原则

1. **完全确定性,零 LLM 调用** —— 免费、快速(< 500ms)、无需 API key
2. **诚实优先** —— 缓存 miss 就明说 unknown,绝不硬猜
3. **单遍文件遍历** —— N 个依赖 × M 个 breaking changes,只扫一次项目文件

## 数据流

```
greenbump --scan [--json] [--no-impact]
  ↓
detectOutdatedAll(pm, cwd) → 过时依赖列表(已支持 monorepo)
  ↓
对每个依赖收集"探针"(不改代码的搜索模式):
  ├─ Tier A: 内置 codemod 索引(零 IO)
  │   codemodsForUpgrade(name, from, to) 匹配 BUILTIN_CODEMODS
  │   → Probe{ pattern: transform.find, description, rewrite: transform.replace }
  │
  └─ Tier B: changelog digest 缓存(只读)
      readDigestFromCache(name, from, to)
      → BreakingChange[] → 每条生成 1-2 个探针(oldApi 的关键词)
      → 缓存 miss → status: "unknown"
  ↓
collectProbes() → 合并去重所有探针(通常 < 100 个)
  ↓
IndexWalker.scan(cwd, probes) → 单次遍历项目,每行对所有探针匹配
  → { probe → [{ file, line, excerpt }] }
  ↓
assembleScanReport() → 按依赖分组,统计 filesMatched / locationsMatched
  ↓
--json → JSON.stringify(report)
否则 → formatScanImpact(report) 渲染文本
```

## 模块划分

### 新建 4 个文件

**`src/engine/scan/probes.ts`** — 把 breaking change 转成搜索探针
```ts
export function probesFromChange(c: BreakingChange): { pattern: string; approx: boolean }[]
export function probesFromCodemod(c: Codemod): { pattern: string; rewrite: string }[]
export function codemodsForUpgrade(name: string, from: string, to: string): Codemod[]
```

关键规则:
- 主探针 = `oldApi.split("(")[0].trim()`,长度 >= 4 才用
- 裸标识符(如 `describe`)→ 只在 import 了对应包的文件里搜索(两级门控)
- 主探针过短 → 提取 `.identifier` 中最长的成员名,标 `approx: true`

**`src/engine/scan/indexer.ts`** — 单遍文件遍历
```ts
export async function scanOnce(
  cwd: string,
  probes: Probe[],
  opts: { perProbeCap: number }
): Promise<{ hits: RawHit[]; truncatedProbes: Set<string> }>
```

实现要点:
- 沿用 fixer.ts 的 `IGNORE_DIRS` / `SEARCHABLE_EXT` 集合(提为共享常量)
- 每行对每个探针做正则匹配,记录 `{ probeKey, file, line, excerpt }`
- 每探针 hard cap 200 个命中,超过即 `truncated: true` 并停止记录该探针
- 敏感文件用现有的 `isSensitivePath()`(guard.ts:14)排除

**`src/engine/scan/impact.ts`** — 编排层
```ts

export async function buildScanReport(
```

**`src/engine/scan/detect.ts`** — 每个依赖的 detection 生成

```ts
export async function readDigestFromCache(
  packageName: string, from: string, to: string
): Promise<BreakingChange[] | null> {
  const cache = getCache();
  await cache.init();
  const cached = await cache.getLlmFix(`digest::${packageName}--${from}--${to}`);
  if (!cached) return null;
  try {
    return JSON.parse((cached.edits as any)["__digest__"] ?? "[]");
  } catch { return null; }
}
```

## 边界情况处理

| 情况 | 处理 |
|---|---|
| **缓存 miss 且无 codemod** | `status: "unknown"`,输出一行灰色提示,引导用户先跑一次 `greenbump <name>` 沉淀缓存 |
| **探针命中 1000+ 次**(如 `_.get`) | 每探针 200 hard cap,`truncated: true`,数字降级为下界 |
| **裸标识符误报**(如 `describe`) | 两级门控:先扫 `from 'pkg'` import,只在 import 了该包的文件里搜索裸标识符 |
| **monorepo** | `detectOutdatedAll` 已返回 `workspacePath`,扫描范围按 workspace 分,输出 file:line 统一为 repo-root 相对路径 |
| **正则编译失败** | 降级为转义字面量(同 fixer.ts 的策略) |

## 不要做的事

- ❌ **绝对不在 scan 里调 LLM** —— 缓存 miss 就标 unknown,这是功能不是 bug
- ❌ **不缓存影响面结果** —— 结果 = f(代码库),代码天天变,缓存无意义
- ❌ **不改 `digestChangelog` 的调用逻辑** —— 只新增 `readDigestFromCache`,不动现有代码
- ❌ **不给 scan 加 exit code** —— 保持 read-only 语义,始终 exit 0
