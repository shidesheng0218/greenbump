# 任务 A：验证器闭环反馈

## A.1 问题（这是当前最大的正确率漏洞）

现在 `src/engine/run.ts` 的流程是：

```
升级依赖 → 跑 build/test → 坏了 → runFixLoop()（AI 改代码）
                                        ↓
                              AI 认为修好了（build/test 绿）
                                        ↓
                     运行静态分析 / AST 分析 / 沙箱 / 性能检测
                                        ↓
                   发现问题 → 只是设置 summary.needsReview = true
                                        ↓
                                    结束了
```

**关键问题**：验证器发现的问题**从来没有回送给 AI**。

具体在 `src/engine/run.ts` 约 443-500 行：

```typescript
const staticResults = await runStaticAnalysis(cwd, { strictLint: false });
const typesFailed = staticResults.some(r => r.stage === "types" && !r.passed);

if (typesFailed) {
  log("⚠️  TypeScript type check failed after fix");
  summary.needsReview = true;      // ← 只打个标记，然后就没有然后了
}
```

后果：
- AI 改完代码，`npm test` 过了，但引入了 3 个 TypeScript 类型错误 → 工具只报告"需要人工 review"，AI 完全不知道自己错了
- AI 悄悄改掉了一个导出的函数签名（下游会炸）→ 同样只是报告
- 用户拿到一个"绿的但其实是坏的"的 PR

**这不是设计取舍，是缺失的反馈回路。** 修复循环只有在 build/test 失败时才会再迭代一轮；一旦 build/test 过了，它就退出了，后续所有验证器的发现都是单向通知。

## A.2 目标

把验证器发现的**可操作问题**回灌进修复循环，让 AI 有机会自己修好，而不是把问题丢给人类。

改造后的流程：

```
升级 → build/test 坏 → runFixLoop()
                          ↓
                   AI 改代码，build/test 绿
                          ↓
              ★ 运行增强验证（类型检查 + AST）
                          ↓
              有问题？→ 把问题作为新的失败上下文，再跑一轮修复
                          ↓
              没问题 → 正常结束
```

## A.3 具体实现

### A.3.1 扩展 `runFixLoop` 的验证回调

**文件**：`src/agent/fixer.ts`

当前 `runFixLoop` 内部用 `runChecks(pm, cwd, checkOverrides)` 判断是否修好（这是唯一的成功判据）。

新增一个可选的**增强验证回调**，在基础 check 通过之后再执行：

```typescript
// 新增类型
export interface EnhancedVerification {
  /** true = 还有可操作的问题需要 AI 继续修 */
  hasIssues: boolean;
  /** 喂给 AI 的问题描述（人类可读，会进入下一轮 prompt） */
  report: string;
  /** 问题摘要，用于日志 */
  summary: string;
}

export interface FixOptions {
  // ...已有字段
  /**
   * 在基础 build/test 通过后运行的额外验证。返回 hasIssues=true 时，
   * 循环会带着 report 继续下一轮，而不是退出。
   */
  verifyEnhanced?: (cwd: string) => Promise<EnhancedVerification>;
}
```

**循环改造逻辑**（`runFixLoop` 内部，找到 `run_check` 工具执行后判定成功的位置）：

```
原逻辑：
  if (check.ok) → 认为修好 → return fixed: true

新逻辑：
  if (check.ok) {
    if (opts.verifyEnhanced) {
      const v = await opts.verifyEnhanced(cwd);
      if (v.hasIssues && 还有剩余轮数 && 未超过 token 预算) {
        // 把问题作为新的工具结果追加到对话里，继续循环
        messages.push({
          role: "user",
          text: `Build and tests pass, but additional verification found problems that must be fixed:\n\n${v.report}\n\nFix these without breaking the build/tests.`
        });
        continue;   // 进入下一轮
      }
    }
    return fixed: true;   // 真正完成
  }
```

### A.3.2 在 `run.ts` 里构造这个回调

**文件**：`src/engine/run.ts`

把当前"事后检查"的逻辑抽成一个函数，同时用于两处：
1. 传给 `runFixLoop` 作为 `verifyEnhanced`（循环内反馈）
2. 循环结束后仍然运行一次，用于填充 `RunSummary`（保证摘要信息不丢失）

要回灌的问题类型（**只回灌可操作的，其余仍然只做标记**）：

| 验证器 | 是否回灌 | 理由 |
|---|---|---|
| TypeScript 类型检查失败 | ✅ 回灌 | AI 完全有能力修类型错误，而且有明确的错误信息 |
| AST 检测到**导出的符号被删除/签名变更** | ✅ 回灌 | 这是真实破坏，AI 应该尝试恢复 |
| AST 检测到新增 `any` | ❌ 不回灌 | 这是风格问题，不是错误，回灌会浪费 token |
| ESLint 警告 | ❌ 不回灌 | 非阻塞，且噪音大 |
| 可疑变更（改了测试文件） | ❌ 不回灌 | 这是给**人类**的信号，不是给 AI 的。回灌可能导致 AI 把测试改回去掩盖问题 |
| 沙箱验证失败 | ❌ 不回灌（本次不做） | 成本高、迭代慢，留到后续版本 |
| 性能回归 | ❌ 不回灌（本次不做） | 同上 |

**回灌报告的构造**（在 `run.ts` 里）：

```typescript
async function runEnhancedVerification(
  cwd: string,
  fix: FixResult,
): Promise<EnhancedVerification> {
  const problems: string[] = [];

  // 1. TypeScript 类型错误
  const staticResults = await runStaticAnalysis(cwd, { strictLint: false });
  const typeErrors = staticResults
    .filter(r => r.stage === "types" && !r.passed)
    .flatMap(r => r.warnings || []);
  if (typeErrors.length > 0) {
    problems.push(
      `TypeScript type errors (${typeErrors.length}):\n` +
      typeErrors.slice(0, 10).map(w => `  - ${w}`).join("\n")
    );
  }

  // 2. AST：导出的符号被删除或签名变更（不含任何新增 any 的报告）
  if (fix.editedFiles.length > 0) {
    const ast = await analyzeApiChanges(cwd, fix.editedFiles, (p) => readFromGitHead(cwd, p));
    const critical = ast.changes.filter(c =>
      c.kind === "export-removed" || c.kind === "signature-changed"
    );
    if (critical.length > 0) {
      problems.push(
        `Public API surface changed (downstream code may break):\n` +
        critical.slice(0, 10).map(c => `  - [${c.file}] ${c.detail}`).join("\n")
      );
    }
  }

  return {
    hasIssues: problems.length > 0,
    report: problems.join("\n\n"),
    summary: problems.length > 0 ? `${problems.length} issue category(ies)` : "clean",
  };
}
```

### A.3.3 必须实现的收敛保护

回灌有死循环风险，必须加保护。以下三条**缺一不可**：

1. **复用已有的 `maxRounds` 上限**（默认 15）——不要新增轮数预算，避免两套预算互相打架。
2. **问题去重**：连续两轮拿到**完全相同**的验证报告 → 判定为"AI 修不动"，立即退出循环并设 `needsReview = true`。用一个 `Set<string>` 存历次报告的 hash。
3. **token 预算复用 `maxTokens`**：如果设置了 `--max-tokens`，增强验证轮同样受其约束。

另外：增强验证本身有成本（TypeScript 编译可能几秒到几十秒）。建议**默认开启**，并提供 `--no-enhanced-loop` 关闭开关（用于极慢的项目）。

### A.3.4 RunSummary 的改动

新增字段，让用户能看到"这个修复是靠闭环反馈救回来的"：

```typescript
export interface RunSummary {
  // ...已有
  /** 增强验证回灌救回来的轮数（0 = 一次就过） */
  enhancedRounds?: number;
}
```

在 `format.ts` 的摘要框里，当 `enhancedRounds > 0` 时输出一行，例如：
```
│ enhanced loop   2 extra round(s) — type errors fixed automatically
```

## A.4 验收标准（必须全部满足）

1. **单元测试**：新增测试覆盖以下场景（放在 `src/agent/fixer.test.ts`）
   - 基础 check 通过 + `verifyEnhanced` 返回 `hasIssues: false` → 正常结束，`fixed: true`，不额外调用 LLM
   - 基础 check 通过 + `verifyEnhanced` 第一次返回 `hasIssues: true`、第二次 `false` → 循环多跑一轮，最终 `fixed: true`，且**第二轮确实收到了问题描述**（断言 provider 收到的 messages 里包含报告内容）
   - `verifyEnhanced` 连续返回**完全相同**的报告 → 循环提前退出，`needsReview: true`，不会无限循环
   - 未提供 `verifyEnhanced` 时，行为与现在**完全一致**（回归保护，现有测试必须全绿）

2. **`run.ts` 层测试**：用 stub provider 模拟"AI 修好了 build 但引入类型错误"，断言最终 `RunSummary.enhancedRounds > 0`

3. **手动端到端验证**：构造一个真实场景——一个 TypeScript 项目，升级某个依赖后 AI 会引入类型错误，确认工具能自己修好。**请在 PR 描述里附上实际运行日志。**

4. `npm test` 全绿（现有 191 个测试一个都不能挂）

## A.5 不要做的事

- ❌ 不要回灌"可疑变更"（改测试文件）——那是给人的信号，回灌会诱导 AI 掩盖问题
- ❌ 不要动 tier 1-3 的逻辑（codemod / 学习模式 / 缓存），本次只改 tier 4 循环
- ❌ 不要引入新的轮数或 token 预算变量，复用 `maxRounds` / `maxTokens`
- ❌ 不要回灌 ESLint 警告和性能/沙箱结果（成本高、迭代慢、噪音大）

# 任务 B：可复现的 Benchmark 套件

## B.1 问题

`README.zh-CN.md` 第 118 行写着：

```
- 🎯 **95%+ 准确率** — 生产级验证
```

**这个数字没有任何可复现的依据。** 仓库里没有 benchmark、没有 fixture、没有评测脚本。

这有两个后果：
1. 对外：用户/评审一旦追问"怎么测出来的"，无法回答，是信任风险
2. 对内：**任何优化都无法证明有效**。做任务 A 的时候你没法说"准确率从 X 提升到了 Y"，只能靠感觉

## B.2 目标

建立一套**可复现、可扩展、能当 CI 跑**的评测套件，输出真实的成功率数字。

## B.3 具体实现

### B.3.1 Fixture 结构

新建目录 `benchmarks/`：

```
benchmarks/
  README.md                    # 如何新增 fixture、如何跑
  cases/                       # 每个 case 一个目录
    express-4-to-5-codemod/
      case.json                # case 元数据（见下）
      repo/                    # 一个最小可运行的 git 仓库
        package.json
        src/...
      expect.json              # 期望结果（见下）
    zod-3-to-4-errors/
    react-router-5-to-6-switch/
    typescript-type-error/     # 这个故意需要 LLM 修，用于测 tier 4
    ...
  run.ts                       # 评测入口
```

`case.json` 格式：

```json
{
  "name": "express-4-to-5-codemod",
  "dep": "express",
  "from": "4.19.2",
  "to": "5.0.1",
  "ecosystem": "npm",
  "description": "Express 5 removed app.del — should be fixed by the tier-1 codemod",
  "expectedTier": 1
}
```

`expect.json` 格式：

```json
{
  "shouldFix": true,
  "forbiddenPatterns": ["app\\.del\\("],
  "requiredPatterns": ["app\\.delete\\("],
  "forbiddenFileChanges": ["package.json", "package-lock.json", "**/*.test.js"]
}
```

`forbiddenFileChanges` 是关键——它能抓到"AI 偷偷改测试让 CI 变绿"这类作弊。

### B.3.2 评测入口 `benchmarks/run.ts`

要求：

1. 遍历 `benchmarks/cases/*/`
2. 对每个 case：
   - 把 `repo/` 复制到临时目录（**不要原地跑，会污染 fixture**）
   - `git init` + 初始 commit（greenbump 需要 git 仓库）
   - 在独立的 `GREENBUMP_CACHE_DIR` 和 `GREENBUMP_STATS_DIR` 下运行
   - 调用 `run()`（从 `src/engine/run.ts` 导入），传 `noGit: false`
3. 检查结果：
   - `summary.fixed` 是否符合 `expect.shouldFix`
   - `forbiddenPatterns` 是否出现在改动后的文件里
   - `requiredPatterns` 是否出现
   - `forbiddenFileChanges` 是否被触碰
4. 输出**机器可读的 JSON + 人类可读的表格**：

```
case                              result  tier  tokens   duration
express-4-to-5-codemod            PASS    1     0        8.0s
zod-3-to-4-errors                 PASS    1     0        7.9s
react-router-5-to-6-switch        PASS    1     0        9.1s
typescript-type-error             FAIL    -     12400    45.2s

Summary: 3/4 passed (75%)
  tier 1 (codemod):  3
  tier 4 (LLM):      1 attempted, 0 succeeded
  total tokens:      12,400
```

5. **支持 `--case <name>` 只跑单个 case**（开发时用）
6. **支持无 API key 运行**：没有 key 时自动跳过需要 LLM 的 case，只跑 tier 1-3 的 case，并在报告里明确标注"LLM cases skipped"

### B.3.3 首批至少 8 个 case

覆盖不同难度层次：

| Case | 测试目标 | 期望 tier |
|---|---|---|
| `express-4-to-5-codemod` | `app.del` → `app.delete` | 1 |
| `express-4-to-5-sendstatus` | `res.send(404)` → `res.sendStatus(404)` | 1 |
| `zod-3-to-4-issues` | `error.errors` → `error.issues` | 1 |
| `react-router-5-to-6-switch` | `<Switch>` → `<Routes>` | 1 |
| `lodash-pluck` | `_.pluck` → `_.map` | 1 |
| `no-fix-needed` | 升级不破坏任何东西（验证不误报） | - |
| `typescript-type-error` | 升级导致类型错误，需要 LLM 修 | 4 |
| `multi-file-breakage` | 破坏跨越 3 个文件，需要 LLM 修 | 4 |

**注意**：最后两个 case 需要真实 API key 才能跑，且会消耗 token。请确保它们在无 key 时能被干净地跳过。

### B.3.4 接入 CI

**文件**：`.github/workflows/ci.yml`

新增一个 job，**只跑不需要 API key 的 case**：

```yaml
  benchmark:
    name: Benchmark (no-LLM cases)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: node dist/benchmarks/run.js --no-llm
```

在 `package.json` 加脚本：

```json
"bench": "npm run build && node dist/benchmarks/run.js",
"bench:no-llm": "npm run build && node dist/benchmarks/run.js --no-llm"
```

## B.4 验收标准

1. `npm run bench` 能跑完全部 case 并输出表格 + JSON 汇总
2. `npm run bench:no-llm` 在没有 API key 的环境下**不报错**，只跑 tier 1-3 的 case
3. CI 里的 benchmark job 全绿
4. `benchmarks/README.md` 说清楚如何新增一个 case（给未来贡献者看）
5. 跑完后，**根据实测结果修正 README 里的准确率表述**：
   - 如果实测 8/8 → 可以写 "8/8 benchmark cases pass"
   - 如果有失败 → 如实写明，并列出已知失败场景
   - **绝对不要在没有依据的情况下保留 95%+ 这种数字**

## B.5 不要做的事

- ❌ 不要把 fixture 做成需要联网下载依赖的重型项目（保持最小化，`npm install` 秒级完成）
- ❌ 不要在 fixture 里跑真实的 `npm install` 之外的重量级操作
- ❌ 不要为了让 benchmark 好看而调整断言；benchmark 的价值在于**诚实**

## 五、有疑问时的判断原则

1. **优先复用已有抽象**，不要新造。比如判断依赖是否被破坏，已经有 `analyzeApiChanges`；判断改动是否可疑，已经有 `detectSuspiciousChanges`。
2. **回灌给 AI 的东西必须是可操作的**。如果你不确定 AI 拿到这条信息能不能改对，就不要回灌，改成标记给人类。
3. **任何有成本的操作都要有开关和预算上限**。
4. **诚实优先**：benchmark 数字、README 宣称，宁可写得保守也不要注水。这个项目的核心卖点就是"可靠"，一旦被发现夸大就全盘皆输。
